# План проекта: калькулятор формы 910.00

Этот документ объясняет, что это за проект, из чего он сделан
и по каким правилам он должен развиваться дальше. Написан простым
языком: если что-то непонятно, значит объяснение плохое, и его
нужно переписать проще, а не считать, что читатель обязан
разбираться в программировании.

Живой сайт: https://ustuf.github.io/910/
Код: https://github.com/Ustuf/910


## 1. Что это за проект

Это калькулятор для одной конкретной налоговой формы в Казахстане,
она называется 910.00. Такую форму сдают индивидуальные
предприниматели, которые платят налоги по упрощённой схеме.

Человек открывает страницу, вписывает свой доход, зарплаты
работников (если они есть), выбирает регион и год, а сайт сам
считает все нужные суммы: налог, взносы за пенсию, медицинскую
страховку и так далее. Это избавляет человека от необходимости
разбираться в бухгалтерии самому или вручную искать актуальные
ставки и проценты.

Сайт рассчитан на обычного человека, а не на бухгалтера: везде,
где возможно, программа подставляет значения сама (например,
ставку налога по региону) и объясняет простыми словами, что
означает та или иная строка формы.


## 2. Из чего сделан сайт (расшифровка технологий)

Сайт «сделан из» нескольких простых строительных материалов.
Дальше объяснение каждого, как для человека, который вообще
не программирует.

### HTML, скелет страницы

Представьте дом. HTML, это как стены, комнаты, двери, то, из
чего дом состоит. Точнее: HTML описывает, какие на странице есть
поля для ввода, кнопки, таблицы, заголовки. Но не то, как это
выглядит, и не то, что происходит по клику.

В нашем проекте это файл `html/index.html`.

### CSS, покраска и оформление

CSS, это как обои, краска, шторы, мебель в доме. Он не меняет,
сколько в доме комнат, но меняет, как всё выглядит: какого цвета
кнопка, насколько круглые у неё углы, где что расположено
на экране.

В нашем проекте это файл `html/css/style.css`.

### JavaScript (JS), мозг страницы

JavaScript, это как электричество и «умные» устройства в доме,
то, что заставляет вещи работать. Если человек нажал кнопку
и что-то произошло: посчиталась сумма, появилось предупреждение,
открылась другая вкладка, всё это сделал JavaScript.

В нашем проекте это файл `html/js/app.js`. Именно здесь лежат
все формулы расчёта налогов и взносов.

### localStorage, память браузера

Это маленький блокнот внутри самого браузера человека. Когда
кто-то вводит свои данные, они записываются в этот блокнот
и остаются там, даже если закрыть вкладку или выключить
компьютер. Блокнот у каждого свой: то, что записал один человек
в своём браузере, не видно никому другому, и на сайт (на сервер)
эти данные никогда не отправляются.

Именно поэтому в форме можно спокойно вводить ИИН, доход, зарплаты
работников: эти данные никуда не улетают, они остаются только
у человека на компьютере.

### Git, история изменений

Git, это дневник, который запоминает вообще каждое изменение
в коде: кто, что и когда поменял. Если что-то сломалось, всегда
можно открыть дневник и вернуться на любой момент назад.

### GitHub, облачный дом для кода

GitHub, это сайт, где хранится копия этого дневника (Git),
доступная из интернета. Можно представить его как облачную
папку, но с историей всех версий, а не только с последним
файлом.

Наш адрес на GitHub: https://github.com/Ustuf/910

### GitHub Pages, превращение кода в сайт

Это встроенная в GitHub услуга: она берёт файлы HTML, CSS и JS
из репозитория и показывает их как обычный сайт по ссылке,
бесплатно.

### GitHub Actions, робот-помощник

Это автоматический робот, который живёт на GitHub. Каждый раз,
когда в проект сохраняются изменения, робот сам, без участия
человека, забирает новые файлы и выкладывает их на сайт заново.
Инструкция для этого робота лежит в файле
`.github/workflows/pages.yml`.

### Итог: как всё это работает вместе

1. Кто-то (я или пользователь через Claude Code) меняет файлы
   в папке `html`.
2. Git запоминает, что именно изменилось.
3. Изменения отправляются на GitHub.
4. Робот GitHub Actions видит новые файлы и выкладывает их
   на сайт `ustuf.github.io/910`.
5. Человек открывает сайт в браузере, вводит свои данные,
   JavaScript их считает, а localStorage запоминает их
   у него в браузере.

Никаких серверов, баз данных или платных сервисов в этой цепочке
нет. Всё, что видит пользователь, это обычный набор файлов,
который умеет считать сам, прямо в браузере.


## 3. Как устроены папки и файлы

```
910/                          корень проекта (репозитория)
├── html/                     всё, что видит и открывает браузер
│   ├── index.html            скелет страницы
│   ├── css/
│   │   └── style.css         оформление
│   └── js/
│       └── app.js            вся логика и расчёты
├── .github/
│   └── workflows/
│       └── pages.yml         инструкция роботу-публикатору
├── README.md                 короткое описание для человека, который
│                              впервые открыл проект
├── PLAN.md                   этот файл: полное описание и правила
├── LICENSE                   разрешение на использование кода другими
└── .gitignore                список файлов, которые Git не должен
                               запоминать (временные, мусорные)
```

Правило простое: **папка `html` и есть сайт**. Всё, что внутри
неё, публикуется по ссылке. Всё, что снаружи (README, этот план,
лицензия), нужно только людям, которые смотрят на код, и на сам
сайт не попадает.


## 4. Правила архитектуры проекта

Архитектура, это просто «правила, по которым разложены детали
конструктора», чтобы через полгода, вернувшись к проекту, можно
было быстро понять, что где искать и не сломать то, что уже
работало.

### Правило 1. Один файл, одна работа

- `index.html` отвечает только за то, какие на странице есть
  элементы (поля, кнопки, таблицы). Он не содержит формул расчёта.
- `style.css` отвечает только за внешний вид. Он ничего не
  считает и не хранит данные.
- `app.js` отвечает только за логику: расчёты, реакцию на клики,
  сохранение данных. Он не описывает, как что-то должно выглядеть
  (это работа CSS).

Если нужно поменять цвет кнопки, это правки в `style.css`.
Если нужно поменять формулу расчёта, это правки в `app.js`.
Смешивать это в одном месте нельзя, иначе через полгода будет
невозможно быстро найти нужное место.

Единственное разрешённое исключение: `app.js` сам строит
разметку таблиц (потому что строки таблиц зависят от введённых
данных и их нельзя заранее прописать в HTML). Это нормально
и сделано специально.

### Правило 2. Данные живут в одном месте

Все данные, которые ввёл человек (ИИН, доход, зарплаты,
регион и так далее), хранятся в одном большом объекте с именем
`S` внутри `app.js`. Ничего не должно храниться «где-то ещё»,
например, растасовано по отдельным переменным в разных местах.
Так проще гарантировать, что при сохранении и загрузке ничего
не потеряется.

### Правило 3. У каждого пользователя свой профиль

Один и тот же браузер может хранить несколько профилей (например,
если сайтом пользуются несколько разных ИП с одного компьютера).
Все профили лежат в localStorage под одним ключом, а какой из
них сейчас открыт, отмечено отдельно. Новые поля данных всегда
добавляются с проверкой «а если у старого профиля этого поля
ещё нет», чтобы у людей, которые уже пользовались сайтом раньше,
ничего не сломалось после обновления.

### Правило 4. Настоящие цифры отделены от формул

Ставки налога, размеры МРП и МЗП, проценты по годам, все эти
цифры собраны в начале `app.js`, в понятных таблицах-справочниках
(`YEARS`, `REGIONS`, `REGION_RATE_2026` и так далее). Сами формулы
расчёта их оттуда просто берут. Это значит:

- чтобы добавить новый год, нужно дописать одну строку в таблицу
  `YEARS`, а не искать формулы по всему файлу;
- чтобы поправить ставку по региону, нужно поправить одну строку
  в `REGION_RATE_2026`, а не логику расчёта.

### Правило 5. Если данных не хватает, честно об этом сказать

Если программа не знает точную ставку налога для региона или
года, она не имеет права её угадывать. Вместо этого она подставляет
общую (базовую) ставку и явно предупреждает человека, что нужно
проверить цифру самому. Ошибиться в реальных деньгах человека
хуже, чем показать предупреждение.

### Правило 6. Один способ ввести один и тот же факт

У каждого поля должен быть только один способ его заполнить.
Например, раньше код налогового органа можно было выбрать из
списка и одновременно вписать вручную в соседнее поле, это
приводило к путанице, какое значение настоящее. Такое запрещено:
если для поля есть подсказки, они должны попадать в то же самое
поле, а не в отдельное.

### Правило 7. Ничего лишнего не отправляется наружу

Сайт не должен ничего отправлять на сервер или в интернет.
Все расчёты происходят прямо в браузере человека, а данные
хранятся только в localStorage. Если в будущем понадобится
что-то отправлять наружу (например, синхронизация между
устройствами), это отдельное большое решение, которое нужно
обсуждать отдельно, а не добавлять между делом.

### Правило 8. Сайт публикуется только из папки `html`

Робот-публикатор (`.github/workflows/pages.yml`) настроен
показывать только содержимое папки `html`. Значит:

- всё, что должно быть видно на сайте, кладём внутрь `html`;
- всё, что не должно попасть на сайт (документация, лицензия,
  настройки), кладём снаружи `html`, в корень проекта.

### Правило 9. Текст внутри сайта, простой и не «от ИИ»

Подсказки и предупреждения внутри самой формы должны звучать как
обычная бухгалтерская программа, а не как ассистент, который
всё объясняет разговорным тоном. Никаких длинных цветных рамок
с дружелюбными подсказками там, где это просто справочная
информация. Цветная рамка-предупреждение допустима только
там, где это настоящая ошибка или предупреждение (превышен
лимит дохода, не указан обязательный код и так далее).


## 5. Правила ведения документации

Документация, это тексты, которые объясняют проект, а не
делают расчёты. У проекта их два вида:

### README.md, короткое знакомство

Читает человек, который в первый раз открыл репозиторий и
за одну минуту хочет понять: что это, как открыть, что уже
умеет, на что не рассчитывать. README всегда должен быть
коротким. Если описание одной возможности разрослось на
несколько абзацев, скорее всего, ему место в этом файле
(PLAN.md), а не в README.

### PLAN.md, этот файл, полное описание и правила

Читает человек (или следующая сессия работы над проектом),
которому нужно понять устройство проекта целиком: из чего он
сделан, почему сделан именно так и по каким правилам вносить
изменения. Обновляется, когда:

- меняется структура папок и файлов;
- появляется новое важное правило («так теперь не делаем»);
- меняется способ публикации сайта или хранения данных.

Не обновляется по мелочам (например, из-за исправления одной
формулы расчёта), такие изменения видно прямо в истории Git,
отдельно описывать их здесь не нужно.

### Общие правила текста в документации и в переписке

- Простой язык, без непонятных слов. Если термин необходим
  (например, «localStorage»), он объясняется сразу же, простыми
  словами, как для человека без технического образования.
- Без длинного тире нигде: ни в коде, ни в документации, ни
  в текстах внутри самого сайта. Вместо него, двоеточие, запятая
  или отдельное предложение.
- Комментарии в коде объясняют «почему так», а не «что делает
  эта строчка» (что делает строчка, обычно и так понятно, если
  код написан читаемо).
- Одна и та же мысль не должна храниться в нескольких документах
  сразу: если что-то написано в README, не нужно дословно
  повторять это в PLAN.md, лучше сослаться.


## 6. Что можно улучшить в будущем (открытые задачи)

Список честных ограничений на сегодня, которые стоит когда-нибудь
закрыть:

- Список кодов налоговых органов заполнен только для Астаны
  и Алматы. Для остальных 18 регионов список подсказок пуст,
  код приходится вписывать полностью вручную.
- Автоматическая ставка налога по региону известна только на
  2026 год и только для 13 из 20 регионов. Для остальных
  показывается предупреждение вместо цифры.
- Состав строк формы соответствует правилам 2026 года. За более
  ранние годы (2023 - 2025) бланк отличался (был социальный налог
  и другое уменьшение налога за работников), но сейчас программа
  считает по правилам 2026 года независимо от выбранного года.
  Это стоит когда-нибудь исправить, если понадобится точный
  расчёт за старые периоды.
- Ставки по регионам собраны вручную из открытых источников,
  а не из официального реестра решений местных властей, и их
  никто не обновляет автоматически. Раз в год (после того как
  местные власти примут решения на новый год) эти цифры нужно
  будет пересматривать заново.
